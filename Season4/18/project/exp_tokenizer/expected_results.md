# expected_results.md —— exp_tokenizer 预期输出范围

供 LabRunner 判读异常。词表 sweep 数据来自真实运行（REAL，本机 CPU 训练）。

## sweep（BPE/Unigram × 4 档词表 × 2 数字策略）

语料：17 篇两域（四大名著 + Python 标准库，约 19 MB）。指标评测样本：
两域 eval 集各 200K 字符（tokenizer 未见过）。长尾统计用训练池抽样 300 篇。

### BPE 实测基线（REAL）

| 词表 | nl bytes/token | 长尾占比(<5次) | embedding 占比(10M档) |
|---:|---:|---:|---:|
| 8k | 3.62 | 5.2% | 22.4% |
| 16k | 4.03 | 12.6% | 36.7% |
| 32k | 4.43 | 28.2% | 53.6% |
| 64k | 4.81 | 47.1% | 69.8% |

### 判读要点

- **三条曲线必须同向单调**：词表增大 → bytes/token 增大（压缩更好）、
  长尾占比升高、embedding 占比升高。任何一条不单调，先查训练语料
  是否一致、词表档位是否真的生效（actual_vocab 应等于目标值）。
- **核心判断的实证**：长尾占比从 5.2% 涨到 47.1%，embedding 占比从
  22.4% 涨到 69.8%——64k 档近一半词表在训练语料中出现不足 5 次，
  同时 embedding 吃掉了 10M 档近七成参数。"把参数花在几乎没被训练的
  位置"就是这两条曲线的交点。
- **数字策略差异在 BPE 上很小**（merge 与 single 的 bpt 差 <0.3%），
  因为 BPE 的合并规则本身会部分吸收差异；真正的差异要到算术任务
  评测（train 模式第二阶段）才显现。
- **BPE 覆盖率应为 1.0**（byte-level 无损）；Unigram 覆盖率约 0.91
  （SentencePiece 默认折叠换行/缩进空白，对代码有损，见 README 踩坑 3）。

### Unigram 实测基线

（REAL，`results/Season4/18/tokenizer_sweep_20260924.json`，与 BPE 同语料同指纹）

| 词表 | nl bytes/token | code bytes/token | 长尾占比(<5次) | 覆盖率 |
|---:|---:|---:|---:|---:|
| 8k | 3.64 | 3.51 | 9.3% | 0.9117 |
| 16k | 4.04 | 4.01 | 14.1% | 0.9117 |
| 32k | 4.42 | 4.20 | 28.2% | 0.9117 |
| 64k | 4.73 | 4.31 | 48.7% | 0.9117 |

对照 BPE 的两点差异（都是文章素材）：

- **nl 域压缩率两算法几乎一致**（8k 档 3.64 vs 3.62；bytes/token 越大压缩
  越好，64k 档 Unigram 4.73 < BPE 4.81，即 Unigram 压缩略差）。长尾占比
  Unigram 全面更高（8k 档 9.3% vs 5.2%）：EM 训练把概率质量摊得更碎，
  小词表里就已有更多低频 piece。
- **code 域 single 策略差异显著**：Unigram 64k 档 merge 4.31 比 single
  3.80 高约 13%（以 single 为基数；以 merge 为基数约 12%），BPE 同档
  3.40 vs 3.23 高约 5%。数字逐位切分对代码域的影响在 Unigram 上被放大。
- 覆盖率恒定 0.9117：SentencePiece normalizer 折叠空白的损失与词表大小
  无关（见 README 踩坑 3），BPE 恒为 1.0（byte-level 无损）。

## train（第二阶段：词表对训练侧的影响）

固定 token 预算（2M）与固定配方（nl50 + MinHash0.8 + 开过滤，与 17 篇基准格
同口径）训练 10M 档模型，只换词表。矩阵 6 组：BPE 四档全跑（主轴）+
Unigram 首尾两档（算法对照）。

### 固定架构口径（hidden 384/6 层/6 头，与 17 篇同档）

| 词表 | 总参数（解析） | embedding 占比 | 预期峰值显存方向 |
|---:|---:|---:|---|
| 8k | 10,621,824+3,072,000 | 22.4% | 最低 |
| 16k | +6,144,000 | 36.7% | ↑ |
| 32k | +12,288,000 | 53.6% | ↑ |
| 64k | +24,576,000 | 69.8% | 最高 |

### 固定总参数口径（解析解，不训练）

把总参数锁在 17 篇 10M 档实测 12,971,904，反解每档词表可用的 hidden
（12·H²·L + H·(2L+1+V) = 目标 的正根取整）：

| 词表 | 6120（17 篇基准） | 8k | 16k | 32k | 64k |
|---|---:|---:|---:|---:|---:|
| hidden 上限 | 384 | 372 | 327 | 256 | 170 |

词表从 8k 到 64k，同样参数预算下注意力/FFN 的 hidden 从 372 被挤到 170，
容量减半还多。6120 档反解回 384 与 17 篇实测一字不差，是解析式的交叉验证。

### 实测基线（REAL，`results/Season4/18/tokenizer_train_20260924.json`，6 runs / 4250.05 s）

固定架构口径（hidden 384/6 层/6 头），只换词表：

| 词表 | 总参数 | 峰值显存 | tok/s | 单组耗时 | nl BPC | code BPC |
|---|---:|---:|---:|---:|---:|---:|
| BPE 8k | 13,693,824 | 1588.4 MiB | 52,012.7 | 38.4 s | 8.4433 | 2.5876 |
| BPE 16k | 16,765,824 | 2121.5 MiB | 46,528.1 | 43.0 s | 8.3478 | 2.4768 |
| BPE 32k | 22,909,824 | 3188.9 MiB | 35,402.9 | 56.5 s | 8.1149 | 2.4195 |
| BPE 64k | 35,197,824 | 5330.2 MiB | **1,133.4** | **1763.7 s** | 7.9490 | 2.4152 |
| Unigram 8k | 13,693,824 | 1588.8 MiB | 8,027.2 | 249.0 s | 8.3977 | 2.4433 |
| Unigram 64k | 35,197,824 | 5330.2 MiB | 1,238.3 | 1614.2 s | 7.9303 | 2.2712 |

判读（三条，都是文章素材）：

1. **nl BPC 单调降但增幅收窄**：8.44→7.95 共 −5.9%（8k→16k 只 −1.1%）；
   峰值显存却涨 3.36 倍（1588→5330 MiB）。压缩收益按百分点递减，显存
   代价按倍增长。64k 档在 8 GB 卡上已占 5.3 GB，再大就 OOM。
2. **64k 档吞吐塌方**：tok/s 从 32k 档 35,402.9 掉到 1,133.4（÷31），
   单组训练 56.5 s → 1763.7 s。词表翻倍，logits 张量（batch×seq×vocab）
   翻倍、显存逼近 8 GB 上限，softmax/交叉熵与显存压力共同拖慢每一步。
   "词表大小对速度的影响"不是线性小账，64k 档在消费级卡上是数量级代价。
3. **ppl 不可横比、BPC 才可比的实证**：BPE 64k nl_ppl 7285.67 比
   Unigram 64k nl_ppl 6068.23 高 20%；换算 BPC 后 7.9490 vs
   7.9303，只差 0.24%。ppl 的差来自 token 粒度不同，不是模型能力差。
   code 域 Unigram 64k BPC 2.2712 反而低于 BPE 的 2.4152。
   另：Unigram 8k tok/s 8027 远低于 BPE 8k 的 52,013，训练侧编码路径
   （SentencePiece Python 接口）比 BPE（Rust）慢，属实现差异不是算法差异。

总参数与解析式（vocab×384 + 10,621,824）逐档吻合；488 步、CUDA、
评测集指纹与 17 篇一字不差（nl c25ed1efc3ffcbe2 / code 18a4f35410f92d39）。

### 判读要点（train）

- 词表越大，embedding 参数越多，峰值显存越高（解析式已给出占比，
  实测同向：1588→5330 MiB）。
- 同样 token 预算下，大词表的每 token 承载字符更多，模型见到的文本
  量更大，困惑度（按字符口径折算后）应更低——但要区分"压缩收益"
  与"长尾参数浪费"两个方向的拉扯。实测 nl BPC 单调降但增幅收窄，
  与第 4 章长尾占比单调升对照，交点即区间上界。
- **跨 tokenizer 比困惑度必须用 BPC（bits per char）**：ppl 是每 token
  口径，token 粒度随词表变化不可横比；BPC = loss × tokens / chars / ln2。
- 所有 run 的评测集指纹必须与 17 篇一致（nl c25ed1efc3ffcbe2 /
  code 18a4f35410f92d39），否则跨篇不可比。
- 结果 JSON 一律 `--out` 直写 /mnt/d 挂载路径；WSL /tmp 跨重启不可靠
  （首轮 sweep 结果即因此丢失重跑）。
